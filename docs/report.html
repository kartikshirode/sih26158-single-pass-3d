02

Four findings that changed the design

The obvious model is licensed out of this job

Verified · primary source

VGGT is the highest-profile model for exactly this task. Its Acceptable Use Policy prohibits “Military, warfare, nuclear industries or applications, espionage”. The customer is India’s technical intelligence agency and the problem statement lists military reconnaissance and border mapping among its applications. This applies to both checkpoints — the 2025 “commercial” relicensing is explicitly commercial except military.

Replacement: MapAnything — Apache-2.0 for both code and weights, with no field-of-use restriction. It also wins on merit, which is the argument we lead with: it regresses metric geometry natively where VGGT is scale-ambiguous, and it accepts intrinsics, camera_poses, depth_z and is_metric_scale as first-class inputs — precisely where GPS and flight metadata enter the pipeline.

≤ 1 m absolute is unreachable from consumer GPS — at any frame count

Measured · EXP-05

A GNSS error model with a correlated Gauss–Markov bias, random walk and white noise, over a 600-keyframe pass, 40 trials per condition. The limit is the sensor, not the algorithm.

Facades, not algorithms, cap completeness

Measured · EXP-08

A surface never observed cannot be recovered by any algorithm — only inferred. Coverage is computed within the corridor the aircraft actually overflies, requiring two or more views so the point is genuinely triangulable.

Classical photogrammetry cannot be the spine

Measured · EXP-01

Two conclusions survive the “but a GPU is faster” objection because they concern shape rather than constant factors: exhaustive matching over 179,700 pairs is hours on any hardware, and even sequential matching exceeds the entire budget before SfM begins.

Stated limit CPU-only, synthetic texture, dense stages unmeasured. This bounds the problem from below; it does not predict any specific pipeline’s runtime. A timed OpenDroneMap run on the target GPU remains an open action.

03

Architecture and the 900-second budget

A feed-forward geometry model on the spine; classical photogrammetry demoted to the refinement-and-export tail where it is fast and unmatched. Roughly 18,000 frames are reduced to about 600 keyframes — the figure OpenDroneMap’s own --video-limit default of 500 anchors — then processed in overlapping chunks of ~48 views and stitched through a pose graph anchored on GPS, so drift is bounded globally rather than accumulating along the pass.

S1 INGESTDecode & conditionMetadata auto-detect, GPS time-sync, blur- and baseline-aware keyframing, intrinsics resolution120 s
S2 MASKDynamic objectsSemantic segmentation plus multi-view consistency — the geometric layer needs no class listoverlapped
S3 GEOMETRYFeed-forward reconstructionMapAnything on ~15 overlapping chunks, GPS and intrinsics as priors, inter-chunk pose graph400 s
S4 GEOREFPlace it on EarthRobust Sim(3) to GPS, GPS-prior bundle adjustment, UTM, ellipsoid-to-geoid height60 s
S5 SURFACEMesh, texture, closePoisson meshing, best-view texturing, bounded occlusion closure — every inferred face tagged250 s
S6 EXPORTSix formats and a viewerOBJ · PLY · LAS · GeoTIFF · GLB · FBX60 s
TOTALwith 10 s reserve against the 15-minute requirement900 s
04

Measuring instrument, built first

The evaluation harness was written and unit-tested before the pipeline it will judge, so every architecture choice becomes an experiment rather than an opinion. It is CPU-only, so the absent GPU quota does not block it. 20 of 20 checks pass — and building it first has already caught five real defects.

The trap it exists to prevent

Best-fit alignment silently absorbs georeferencing error. On a model with a real 2.68 m offset, ICP-aligned scoring reports 0.21 m — flattering by 12.8×. The harness therefore always prints absolute and aligned error side by side.

The standard Tanks-and-Temples protocol compounds this: it aligns with a 7-DoF similarity, forgiving scale. A model uniformly 5% too small scores 0.000 m under that protocol and 1.083 m under ours. Our aligner fits no scale and reports scale error as a number in its own right.

The third and fourth are worth stating plainly: a robust estimator tuned below the noise floor is worse than no robust estimator at all, and RANSAC’s value here is a bounded worst case — error flat near 4.1 m however bad the GPS gets — not a better average.

05

Compute: blocked, with a route around it

Blocked · verified Every GPU path on the project’s Google Cloud account is denied, and the cause is a single machine-readable field: ineligibilityReason: NOT_ENOUGH_USAGE_HISTORY. Requests are refused within seconds by an automated gate, so there is no reviewer to appeal to, and asking for less does not help — both 4 GPUs and 1 were refused identically.

  • Compute Engine global gate, L4 and preemptible L4 in Mumbai — all refused.
  • Cloud Run L4 — both the zonal-redundant and non-redundant pools are zero, confirmed by a live deploy that fails admission either way.
  • Two traps recorded so they are not rediscovered: the retired K80/P100/V100 rows showing limit=1 are not usable GPU access, and the quota API lists asia-south1 for Cloud Run L4 while deploying there fails — Cloud Run L4 exists only in asia-southeast1, europe-west1/4, us-central1 and us-east4.

Requests are filed and will be re-evaluated; the gate is a spend-history gate, so the unblocking move is to run ordinary billed CPU work on the project now — which the pipeline’s ingest, georeferencing and export stages need anyway. Meanwhile the Baramati Slurm cluster covers development today. This constraint improved the design: the target deployment is a single 24 GB GPU, because a field mapping system that needs eight of them is not something NTRO can deploy.

06

What we may claim, in writing

Recorded now so it cannot drift under deadline pressure in December.

  • If the dataset carries RTK/PPK — claim ≤ 1 m absolute, evidenced.
  • If it does not — claim ≤ 1 m relative/shape accuracy, which is achievable and is what “metric accuracy without ground control points” conventionally means, and state the absolute georeferencing error separately and plainly.
  • Never quote the aligned number as though it were absolute.
  • Completeness is reported against two denominators — observable surface, and whole scene — because reporting only the first hides a real limitation and only the second penalises us for physics.
  • Every inferred face is tagged and can be hidden in the viewer. A judge who measures a wall we invented should be able to see that we invented it.

Open questions for the organisers — these change what is claimable

Does the dataset include RTK/PPK corrections? Is “≤ 1 m” absolute or relative? Is evaluation against a LiDAR or multi-pass survey reference? Is the single pass nadir or oblique? Unverified Each is currently an assumption on the register, and the design satisfies the strictest reading of all four.
